# 55块2 · tally-book

按 `plan/` 搭建的原生微信小程序项目。

## 当前阶段

- 领域层 `money / calendar / plan / ledger` 与视图投影层 `ledger-view`
- 五期数字校验、五个 Tab 页面 + 全量流水页
- 预算情景（省/中/松）切换：已执行期次以流水为准，未执行期次与储蓄目标重算
- 划额可补：批次首日漏划能在本批任意一天补上，历史上漏划的那天也能从本期页明细补划并结算
- **两段到账（v1.4.0）**：工资日登记工资、生活费日（一般 28 日、固定 ¥2,000）单独登记生活费；
  每笔到账默认按「账单 → 预算池 → 储蓄」安置，**三个口袋各放多少可以自己改**（见下），
  步骤完成状态全部由真实流水派生，两笔到齐且沿用推荐值时期末金额与原计划表逐分一致
- **回退已登记的到账**：工资/生活费登记错了，在发薪日页一键回退 —— 收入连同它当时安置的几笔一起删，
  账本恢复成登记前的样子，之后可以重新登记
- 发薪日第六步「清理上期结余」：把余额宝用不完的余粮按确认转进小荷包（carry_over）；该步是否完成只看这笔真实流水
- 本地导出（CSV / ICS）、JSON 备份与恢复、金额校准、追加式冲正（部分/批量）
- Git 版本控制

项目使用 `.nvmrc` 固定 Node.js `24.21.0`。首次进入项目目录后执行 `nvm use`；若本机尚未安装该版本，执行 `nvm install`。

## 架构约束

- 金额在领域层统一用“分”存储，展示时才转换为元。
- 领域层为纯函数，不依赖微信 API。
- 账户余额由追加式流水派生，不保存不可追溯的死余额。
- `Expense` 是真实支出；还款、预算分配、日终退款均是 `Transfer`。
- 展示层只有一处口径：`domain/ledger-view.js` 的 `buildLedgerEvents` 把四类记录投影成统一“账务事件”，
  今日页、本期页、储蓄页、全量流水页和 CSV 导出全部走这一层；余额仍由 `domain/ledger.accountBalances` 派生，
  视图层不参与任何写账计算。

## 流水视图（2026-09-19）

- 新增页面 `pages/ledger/index`，四个入口：今日页、本期页（含点柱子看当天）、储蓄页、我的页。
- 每条事件带：业务日期 `eventDate`、创建时间 `createdAt`（本地时区渲染）、类型、`kind`、账户方向、金额、备注。
  老数据没有 `createdAt` 时 `exactTime = false`，页面显示“时间未记录”，不伪造时间；排序按
  `eventDate → createdAt → id` 倒序，发薪日多步（同一毫秒写入）按 SOP 顺序 `工资到账 → 生活费到账 → 还账单 → 预算入余额宝 → 转入小荷包 → 清理余粮` 展示。
- 金额符号按“视角账户”计算：今日/本期取工资卡，储蓄页取小荷包，流水页取当前选中的账户筛选；
  未选账户时划转只显示方向不加正负号，避免误读。
- 账户 `OUT` 作为去向显示“支出”，作为来源显示“外部”（工资到账这类入账）。
- 流水页不删除、不改数；唯一的写操作是**冲正**（追加式更正），原记录一个字节都不改：
  - 三种用法：全额冲正剩余可冲额、**部分冲正**（只填错的金额，例如 30 记成 42 就只冲 12）、**批量冲正**（多选一次确认）。
    弹窗会先算清楚连带影响（要不要补退、补多少）再写入。
  - 可冲正的是普通支出与**专项支出**；划转是真实发生的转账、校准本身就是追加差额，都不给冲正入口。
  - 批量冲正是**原子**的：任一条不成立就整体不写，并回传失败位置；同批多条各留自己的补退，逐笔可追溯。
  - 冲正记录落在**原始记录的日期**上，与它同属一个批次（之后切换结算模式也不会错开）。
  - 批次**未封账**：不产生划转，结算时按净支出重算补差与退款；批次**已封账**：把“应退 − 已退”的差额作为一笔
    `daily_refund` 补退（落款今天、带 `batchKey` 归属原批次），因此 `settleDay`/`reopenDay` 天然不会重复退款。
  - 回写 `daySlots` 必须沿用批次记录的 `batchMode`，不能被当前模式覆盖，否则“三日批次 → 切每日 → 冲正旧批次 →
    撤销封账”会让整个三日批次在首日提前退款（`test/reversal.test.js` 锁住）。
  - 冲正记录不可再被冲正，累计冲正不得超过原单金额，计划截止日后账本转为只读。
  - 视图口径：被（部分）冲掉的原单与冲正记录都不计入“有效支出笔数”，金额一律带符号净额；
    “隐藏冲正对”只隐藏完全抵消的成对记录（部分冲正不能隐藏，否则误记会重新冒出来）。
- **备份与恢复**（换机不再靠手抄）：`utils/backup.js` 导出完整 JSON 快照（含 `daySlots` 封账状态、`mode`、
  `openingBalances`、`executedPaydays`）。CSV 仍是给人看的单向导出，不作为恢复入口——它丢了结算依据，
  用它恢复会静默改变退款与补差口径。
  - 恢复有两个入口：`wx.chooseMessageFile` 选聊天里的备份文件、或剪贴板粘贴；都先校验再弹“整体替换”确认。
  - 校验只放“不会写坏账本”的数据通过：流水 id 全局唯一、金额必须是整数分、业务日期必须 `YYYY-MM-DD`、
    冲正必须指向存在的原单且金额为负、`config` 完整、`schemaVersion` 不得高于当前版本。
  - 恢复前自动把当前账本存进 `p5519.rollback`，可在「我的 → 撤销上次恢复」一键退回；新账本写不进 storage
    时立即回退，不留半套状态。误点“重置演示数据”同样能被撤销。
  - `migrate` 把 `periods: []` 也视为缺失并重算，避免恢复一份期次为空的备份后页面失去期次依据。
- 储蓄页新增“小荷包流水”卡片，并用逐笔合计对账派生余额；不一致时直接提示差额原因。
- CSV 改为导出统一流水全量（含流水 ID、业务日期、创建时间、是否精确、类型、明细、金额、方向、账户、备注），
  主出口是写文件 + `wx.openDocument`，失败退回 `wx.shareFileMessage`，最后才复制剪贴板。

## 预算情景（省/中/松）切换口径（2026-09-20 code review 修复）

回答的问题：**已经封账之后，把计划从「中」改成「省」会不会出问题？**
结论：钱不会错，但口径会。下面几条把口径也钉死了（`test/scenario.test.js` 逐条锁住）。

- 情景只决定“往后按多少花”。`domain/plan.periodIncomeTotals` 把每一期的期次流水
  （`payday_income / allowance_income / bill_repay / payday_budget / payday_save`）从账本里读回来，
  `derivePeriods({ dailyBudget, allowanceExpectedDay, ledgerTotals })` 因此不会追溯改写历史期次：
  **两笔收入都到齐**（`fullyFunded`）的期次，预算、转存、累计储蓄一律 = 实际流水；
  其余期次按新日额度重算，`config.targetSavings` 跟随“实际 + 未来计划”的真实轨迹。
  改之前：切一次情景，本期页“本期剩余”凭空少 ¥200.10，而余额宝余额并没有变 → 页面自相矛盾。
  （v1.3.0 之前这里的入口叫 `executedPaydayTotals`，锁定条件是「已执行」；v1.4.0 两段到账后
  改成按 `periodIndex` 归集、锁定条件是「两笔到齐」，函数已删除。）
- 本期页「本期预算池」显示**真实入池额 / 计划池额**（例如 `¥1455.68 / ¥1600.51`），
  并写出「还差 ¥144.83 没进池子，生活费到账后补上」。
- **「预计余粮」用同一个斜杠写法**：`实际 / 全部到齐后`
  = `池里实有多少 − 已记支出` / `计划池额 − 已记支出`。
  例：两笔到齐、预算 1600.51、已花 1 元 → `1599.51`；生活费还没到时是 `1454.68 / 1599.51`。
  两个数相等（池子已满）时斜杠那半自动隐藏。早先只拿计划池额减，
  于是「预算池 1455.68 / 1600.51」下面直接写着「预计余粮 1600.51」，同一张卡自己打自己。
- 相关口径一起对齐：本期页「五期储蓄轨迹」的转存额改念真实流水（`savePlaced`）并把计划值单列；
  ICS 导出的转存事件在两笔到齐后念真实额、一分没存就不再提醒、未到齐时文案写明「计划转存」。
  凡是「实际 / 计划」两个数的地方，一律真实值在前。
- 期次永远是派生数据：`utils/storage.migrate` 每次装载都按“当前情景 + 已执行流水”重算，
  不再靠 `budgetToPool === days * dailyBudget` 的启发式判断缓存是否陈旧
  （恢复一份 `periods: []` 或旧情景的备份，同样得到正确期次）。
- 封账退款/冲正补退本来就和情景无关：额度取当天真实的 `daily_alloc` 流水，
  `应退 = 划入 + 已补差 − 净支出 − 已退`。所以“中情景划入 55.19 → 封账 → 改省 → 撤销封账再结算”
  仍退 25.19；已封账批次冲正 42 元仍补退 42 元；三日批次第 3 天仍按首日划入的 165.57 结算，
  下一批次才用 3×48.29。
- `setScenario(scenario, asOfDate)` 加了护栏：计划截止日后账本只读，情景作为计划参数一并冻结
  （`blocked: 'ended'`），计划未开始时仍可先定情景。返回值带 `frozen` / `replanned` 期次号；
  「我的 → 预算情景」改成二次确认弹窗，如实说明哪几期锁定、哪几期重算；储蓄页期次卡标出「已按实际流水锁定」。
- 未划额批次（没点“今日划额”就先记支出）的补差阈值 `daySlots[start].plannedBudget`
  在**第一笔支出落地那一刻**钉住：否则事后改情景会把阈值从 55.19 搬到 48.29，
  让本来没超支的支出凭空从余额宝补差。它只是阈值口径，`settleDay` 仍只认 `daily_alloc` 流水或 `allocated`，
  所以不会因为一个计划值而“凭空退款”。
- 浸泡验证：完整 136 天剧本（随机支出、划额、封账、冲正、切模式、**随机切情景**）跑 40 个种子，
  全部满足复式记账恒等式（五账户相加为 0）、封账后工资卡归零、视图逐笔合计 == 派生余额、
  已执行期次预算 == 实际 `payday_budget`。

## 划额与批次身份（2026-09-20 code review 修复）

- 早间划额允许**批次内补划**：三天一结时首日漏点，本批任意一天都能补上，额度仍按批次首日入账
  （业务日期 = 批次首日，`createdAt` 记录真实操作时刻），一个批次只会有 `1` 笔 `daily_alloc`。
  否则第 2/3 天按 `dayNumber % 3` 永远划不进去，整批卡在 `not_allocated` 封不了账。
  金额 = 批次实际天数 × 当前情景日额度，被计划截止日截短的尾巴批次不会多划两天。
- **一天只属于一个批次，批次身份一旦登记就不再改写**。`resolveBatchRange` 把三日网格裁到
  不与「已归批日子」冲突的范围，`markBatchSlots` 拒绝改写别的批次的日子。
  修掉一个 v1.1.0 就存在的超退缺陷：单日批次已封账 → 之后切三天一结 → 冲正同网格内另一天，
  已封账批次会被并进 `11-20~11-22` 这样的三日批次，按 3 天额度重算“应退”，
  实测余额宝凭空多收 96.58、工资卡倒贴 96.58（`test/batch-identity.test.js` 锁死）。
- 补差/退款/冲正补退统一走 `allocationOf(current, range, fallback)` 一套口径：
  批次额度优先取实际 `daily_alloc` 流水，其次日槽 `allocated`，再退到 `plannedBudget`，
  最后才按“批次天数 × 当前情景日额度”兜底。
- 页面播报：补划时提示「已补划 ¥144.87（3 天额度，落在批次首日 11-17）」，
  批次未划额时结算提示「本批次还没划额，先点上面的早间划额」。
- `test/soak.test.js` 是浸泡回归：随机支出/漏划额（走补划）/封账/冲正/切模式/切情景跑完整 136 天，
  逐日断言复式记账平衡、已封账批次净额归零、划额都在批次首日、视图逐笔合计 == 派生余额、
  已执行期次预算 == 实际 `payday_budget`。把上面任何一道防线拿掉，浸泡测试立刻失败。

## 过去的某天补划 / 结算入口（2026-09-20）

- 本期页点柱子展开的当天明细里，新增两个入口：**「补划这天额度 ¥X」**与**「结算这天 · 退回余额宝 ¥Y」**。
  每日模式下漏划额的是“已经过去的某一天”，今日页只操作今天，补不了；store 一直支持任意业务日期，
  这里只是把它接给页面。补完必须能立刻结算，否则额度会半浮在工资卡上，所以两个入口成对出现。
- **页面只对“已经发生的日子”写账**：未来的柱子不给按钮，只显示「这天还没到，先把当天的账记实」。
  store 仍接受任意日期（补记、冲正、回溯补划都需要它），日期是否已经到来由视图层判断。
- 预览与写入共用一套口径：`allocationPlan` / `settlementPlan` 是纯决策函数，
  `allocateDay` / `settleDay` 据此写入，`previewAllocation` / `previewSettlement` 原样返回给页面；
  页面不再自己拿日额度估算金额。
- **补划金额沿用该批次已经钉住的额度**（`daySlots[start].plannedBudget`），不是切换后的新情景额度：
  那几天可能已经按旧阈值产生过超支补差，若改按新额度划入，就会出现
  「按 ¥63.73 补了差、只划进 ¥55.19」的窟窿，封账后工资卡凭空短 ¥8.54（浸泡种子 245502 实测）。
  多划的部分结算时整批退回余额宝，不多占用池子。
- 已封账 / 计划未开始 / 计划已结束的日子，入口自动隐藏并给出对应说明；重复补划仍是 `alreadyAllocated`。
- 浸泡测试 `test/soak.test.js` 现在也会随机回到本期更早的某天补划并结算，
  逐日断言：已封账批次净额归零、一批只一笔划额且落在批次首日、复式记账平衡、视图合计 == 派生余额。

## 两段到账：工资日 + 生活费日（v1.4.0，2026-09-24）

SOP 从「五步一次性」改成「六步两段」：① 工资到账（发薪日登记）② 生活费到账（一般 28 日、固定 ¥2,000）
③ 还账单 ④ 入预算池 ⑤ 转存小荷包 ⑥ 清理上期结余。**每一笔到账都按「账单 → 预算池 → 储蓄」安置**，
所以工资不够覆盖「账单 + 池」时不会写出负数：先还账单、剩下的入池，缺口留给生活费
（第 1 期差 ¥144.83、第 2 期差 ¥647.88）。

- `domain/plan.placementFor(period, freeFen)` 是**唯一**的安置算法：只看「这笔钱到来时各目标还差多少」，
  写入（`placementTransfers`）与页面预览（`period.salaryPlan` / `period.allowancePlan`）共用它，页面不自己算。
- `periodIncomeTotals(transfers)` 按期次归集流水：新流水认 `periodIndex`，旧流水按发薪日匹配，
  再兜底按业务日期落在哪一期。旧账本一笔合并入账（v1.3 的 `payday_income` = 工资 + 生活费）
  按「计划工资 + 差额」识别成 `legacyMerged`，**历史流水一字不改**，也不会让用户重复登记 ¥2,000。
- 六步完成状态全部由流水派生（`store.paydayStepStatus`），`togglePaydayStep()` 对任何一步都只返回
  `derived_step`。第 3/4/5 步的判定是 `pendingXxx === 0 && 目标 > 0`，而 `pendingXxx` 与页面文案的分母
  是同一份目标（`billTotal / budgetToPool / saveToPocket`），所以不会出现「勾已打上、文案却说还差 ¥55.27」。
- `setScenario` 的锁定条件是**两笔到齐**（`fullyFunded`）：只登记了工资的期次，已发生的钱不动、
  未安置的目标按新情景重算，池子里多出来的部分成为第六步可清理的余粮，不会蒸发。
- `executePayday()` 保留为「同日到账」兼容入口，但**两段在同一次 commit 里落地**：
  早先分两次提交，第二段写盘失败会返回 `persisted:false`，页面弹「本次改动没有保存」，
  而工资那几笔其实已经存下来了。
- 生活费逾期（本期区间已过还没登记）时，主按钮的默认到账日一律夹到 `[发薪日, min(今天, 本期结束)]`，
  确认弹窗会把这一天念出来；今日页的待登记提醒**扫全部五期**，不只扫今天所属的那一期 ——
  否则第 1 期的 ¥2,000 漏登、人走进第 2 期之后就再没有任何提醒。

## 自选安置：这笔到账放账单 / 余额宝 / 小荷包各多少（2026-09-25）

发薪日页在登记前给出三个输入框（还账单 / 放余额宝 / 存小荷包），**预填推荐值**
（`domain/plan.placementFor` 的「账单 → 预算池 → 储蓄」），改了就以你填的为准，也可以一键「用推荐分配」还原。

- 校验在 **store** 而不是页面（`store.resolveSplit`）：三项都必须是非负整数分、
  **合计正好等于这笔到账金额**、还账单不得超过本期还没还清的部分。
  违反分别返回 `bad_split / split_mismatch / bill_over`，一笔流水都不写。
  页面也当场算合计并禁用按钮，但那只是反馈，不是裁决。
- 不给 `split` 就是推荐值：`executePayday`、浸泡测试、旧调用方一律不受影响。
  **沿用推荐值时，最终余额与 v1.3.0 逐分一致**（已用同一套随机支出脚本对照过）。
- 账单口径随之修正：`period.billTotal` 一律等于计划账单额（`BILL_TOTALS`）。
  它是外部固定义务，既不是计划参数、也不会随情景变化，更不能因为「用户选择少还一点」就跟着缩水 ——
  否则少还的账单会被当成「目标已达成」，第三步凭空打勾、账上看不出还欠多少。
  少还之后第三步会一直不点亮，生活费的推荐值会**优先把账单补齐**。
- 少放余额宝 / 多放余额宝都会当场说清后果：每天的「早间划额」只从池子里出，少放了要靠生活费补，
  补不上工资卡就会透支；多放的部分成为余粮，由第六步真实清进小荷包。
- 备份新增不变量：**每期「已安置 == 已到账」**（`billPlaced + poolPlaced + savePlaced === salaryIn + allowanceIn`）。
  页面会校验合计，但备份文件可能被手改过，少了这条就会凭空蒸发或多出一笔钱。

## 回退已登记的到账（2026-09-25）

「昨天手滑按错了」是真实需求。两段到账一次写 2~5 笔流水（收入 + 安置），
安置又分账单 / 余额宝 / 小荷包三个方向，**用「冲正」一条条补是补不回来的**（冲正只覆盖支出与专项）。
所以发薪日页给了一个「回退这笔到账」：整组逻辑删除，撤销后账本恢复成登记前的样子。

- 整组的身份优先认 `arrivalId`（收入流水用自己的 id，每笔安置流水回指它）。
  **但 `arrivalId` 是后加的字段，之前登记的流水没有它** —— 所以更早的流水按事实认：
  同期次 + 同 `createdAt`（登记是同一毫秒一批写完的）+ 同一天 + 账户流向正好是该 kind 的方向。
  只按日期或只看 kind 会误伤当天别的手工划转；这几条一起卡才准（`test/payday-steps.test.js` 钉住）。
- **入口就在那六步的下面**：那几步的勾是登记到账时按真实流水打上的，所以回退区块紧跟步骤列表，
  不会被下面的分配编辑器挤到看不见的地方。点已完成的那几行也不再只甩一句「不用手勾」，
  第 1/2 步直接指向回退按钮，第 3/4/5 步解释它们由登记时的分配决定，第 6 步指向清理按钮。
- 两笔都登记了时**一次只撤最后一笔**（先生活费、再工资）；顺序反过来余额宝会被算重。
  弹窗里会提示「撤完这一笔，可以再点一次回退工资那笔」。
- **硬阻断只有两种**，因为只有它们会把账做坏：
  | | 原因 |
  | --- | --- |
  | `legacy_merged` | v1.3 那种「一笔写工资+账单+池+转存」的合并入账 —— 它根本没有独立的到账组可以摘，只能走「我的 → 恢复备份」 |
  | `ended` | 计划截止日之后账本只读 |
- **已经划额 / 封账 / 花掉 / 清理过都不阻断**，只如实列出后果。这些并不会破坏记账正确性
  （复式合计照样为 0），只是余额宝或工资卡会显示成负数；重新登记这笔到账就补齐。
  早先把它们当硬阻断是过度保守：昨天按错了、今天已经划过额，就再也退不回去了。
- 撤销本身是追加式的「删掉自己那几笔」，别人的支出、划额、封账记录一笔都不动。
- 备份新增不变量：`arrivalId` 必须指向存在的到账流水，且不能指向自己。

## 第六步「清理上期结余」：余额宝余粮转进小荷包（2026-09-20）

计划表假设预算会被花光（`saveToPocket = totalIn − bill − budgetToPool`），**没花完的钱只会躺在余额宝里，
不算进储蓄**；改小情景后多出来的额度也一样。以前这笔钱只能靠手抄或「金额校准」硬对，现在按 SOP 第六步
把它变成一笔真实划转：

- **入口等两笔到齐**：生活费还没登记时预算池还差 `pendingPool` 才满，此时算出来的「余粮」里
  有一部分正是生活费待补的钱，清走等于提前把生活费花掉。所以发薪日页与储蓄页的清理入口
  都要求 `fullyFunded`，到齐后池子满员，清掉的才是真余粮。
- 口径（纯函数 `domain/plan.poolSurplus`）：
  `可清理余粮 = 余额宝余额 − max(0, 剩余天数 × 当前情景日额度 − 生活费还会补进池子的部分)`，
  负数一律按 0 计。**今天所在的批次已封账 → 今天不再预留**，所以截止日当天结完账，
  最后一期的余粮也还能清干净（`remainingDays = 0`）。
  最后那个减项是 v1.4.0 两段到账补上的：工资日之后预算池还差 `period.allowancePlan.pool` 才满，
  而生活费到账时 `placementFor` 一定会把它补进来，所以它不该占着「现在必须留在池子里」的名额。
  少了这一项，上一期的真实余粮会被这道缺口整个吞掉 —— 第 1、2 期的缺口分别有 ¥144.83 / ¥647.88，
  只要上期余粮小于它，第六步在工资日就永远算出 0（`test/sweep.test.js`、
  `test/payday-steps.test.js` 逐条钉住）。返回值同时给出 `needed / reserve / surplus` 三个数，
  确认弹窗会把「计划开销 ¥X，其中 ¥Y 生活费到账后会补进来，现在只需留 ¥Z」说清楚。
- `store.sweepPoolSurplus` 只写一笔 `carry_over`（余额宝② → 小荷包③，业务日期 = 点确认那天）。
  它与 `surplusPlan` 共用同一份计算，页面显示的金额 = 实际转走的金额；**不点确认就一分钱都不动**。
  转完再点只会算出 0（`skipped`），天然幂等，不需要额外的“已清理”标记。
- 入口两处，都是二次确认弹窗（`utils/sweep.js`）：发薪日页第六步显示「当前可清理 ¥X」+ 按钮，
  储蓄页新增「清理余额宝余粮（第六步）」卡片；计划结束后不再可写，储蓄页只提示
  「余额宝里还留着 ¥X 未清理」。
- 这笔钱**算进实际转存**（储蓄页期次行标「含清理转入 ¥X」），但**不进计划列**：
  `derivePeriods` 的 `saveToPocket` 仍只取 `payday_save`，避免同一笔钱被数两次。
  划转类记录照旧不给冲正入口，要更正只能再转一笔或做校准。
- 踩过的坑（都进了浸泡不变量）：`plannedBudget` 阈值必须和批次身份同时登记，
  否则“单日阈值 + 事后并成的多日批次”会少划一天额度、封账后工资卡凭空短 ¥13.54（种子 324692）。
  现在 `test/soak.test.js` 会随机执行第六步清理，断言：清理前后 `余额宝 + 小荷包` 相加不变、
  清理后余粮收敛为 0、重复清理返回 `skipped`、余额宝不会被转成负数。

## 结算不变量（2026-09-19 code review 修复）

- 早间划额 `daily_alloc`、超支补差 `overspend_cover`、晚间退款 `daily_refund` 三者互不重复：
  余额宝在一个批次上只付出 `划入 + 补差`，退款额 = `max(0, 划入 + 补差 − 批次支出 − 已退)`。
- 三天一结按“批次”（组内第 1 天划入、第 3 天结算）判断超支与退款，不再用单日额度。
- 撤销封账会同步撤销该批次的退款划转，重新结算不会把同一笔钱退两次。
- 结算/校准/专项使用本地时区日期（`domain/calendar.todayKey`），UTC+8 早上 8 点前不会写成前一天。
- 计划流水只允许发生在 `2026-09-24` 至 `2027-02-05`；计划结束后页面转为只读回顾状态。
- 金额校准以追加式差额参与账户余额派生，原始流水保持不变。
- 有未结三日批次时禁止切换结算模式；最后一个批次会在计划截止日收口。
- 第一笔支出落地时同时钉住「该批次的计划阈值」与「批次身份」：三者（阈值、划额金额、退款核算）永远指同一个范围，事后切模式或改情景都搬不动。
- 一天只属于一个批次：批次身份（`batchStart/batchEnd/batchMode`）一旦登记，切换结算模式或事后改动历史都不会把它并进别的批次。
- 冲正/补退只追加流水，不改写历史：`batchNumbers` 是 `settleDay`、`reopenDay`、`reverseExpense` 共用的批次结算口径
  （额度、净支出、已补差、已退款、应退余额），避免出现第二套退款算法。

## 2026-09-23 code review 修复（写入一致性与只读生命周期）

### 2. 计划只读生命周期：一张表说清（P1 + P2）

截止日（`2027-02-05`）之后的可写能力现在明确分三档：

| 能力 | 截止日后 | 理由 |
| --- | --- | --- |
| 计划流水：支出、专项、划额、结算、撤销封账、余粮清理、冲正、发薪日登记 | 禁止（`blocked: 'ended'`） | 历史账务状态不得继续被改动 |
| 计划参数：预算情景、结算模式、SOP 手勾（完成状态一律由流水派生） | 禁止 | 会改写期次口径与历史留痕 |
