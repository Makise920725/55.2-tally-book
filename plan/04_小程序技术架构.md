# 「55块2」技术架构说明

> 一句话概括：**本地优先（local-first）＋ 追加式账本派生余额 ＋ 零后端**的微信小程序。不需要数据库、不需要登录、不需要运维。

---

## 一、四个核心架构决策

| # | 决策 | 反面选项 | 为什么这样选 |
|---|---|---|---|
| 1 | **本地优先**（storage 为主，云只作备份） | 全部走云端数据库 | 记账是高频＋离线场景，断网必须能用；启动 0 延迟；个人云额度有限 |
| 2 | **派生余额，不存死值** | 把「③余额=1855.17」直接写进 storage | ③余额由流水聚合得出。存死值一旦写坏就永久错误；派生可重算、可回溯 |
| 3 | **零后端** | 自建 Node/Java 服务＋MySQL | 单人使用、无协作需求；MVP 阶段一分钱不花也完全够用 |
| 4 | **金额全程用「分」存整数** | 用 float 存元 | 135 天累加，浮点必出 0.01 误差且无法定位；展示层再 ÷100 |

**依赖方向只能向下**：Page 调 Store，Store 调 Domain，Domain 谁都不调（纯函数）。这条决定了一切可测性。

## 三、微信小程序运行时架构（必须知道的底层特性）

```
┌────────── 微信客户端（Native）──────────┐
│ JSBridge / JSAPI / 渲染优化 / 权限管理   │
└─────┬──────────────────────┬───────────┘
   渲染层                  逻辑层
 WebView(WXML+WXSS)      JSCore(无 DOM / 无 window)
 setData ◄──────────────► wx.* API
```

对你这个 App 的直接影响（性能就死在这几条）：

| 特性 | 后果 | 对策 |
|---|---|---|
| 逻辑层没有 DOM/window | 第三方 DOM 库全不能用 | 图表自己写 Canvas，不引 DOM 类库 |
| 两层靠 setData 跨线程通信（要序列化） | 频繁/大块 setData 明显卡顿 | **局部 setData**：只传变化字段；禁止整页 data 重推 |
| 每天结算触发全量聚合 | 135 天 × 多表，低端机可感 | 聚合结果**记忆化缓存**，流水变化才失效 |
| 主包上限 2MB | 素材一多就超 | 图标用 CSS/字体；预置 JSON <10KB；分包 |
| 页面栈最多 10 层 | 深跳会崩 | 5 个 Tab 结构天然规避，不用 navigateTo 套娃 |

## 四、框架选型（三选一）

| 方案 | 适合 | 代价 | 结论 |
|---|---|---|---|
| **原生小程序** WXML/WXSS/JS | 单人维护、包体最小、审核最快 | 无组件生态 | ✅ **推荐** |
| Taro 3（React 语法） | 你熟 React、未来要出 H5 | 构建链＋包体积＋200KB | 要跨端才选 |
| uni-app（Vue 语法） | 你熟 Vue、要多端发布 | 同上，生态较杂 | 要跨端才选 |

> 你的场景是「一个人天天用的工具」，**不需要多端**。写原生，少一层构建工具，bug 少一半。

## 五、状态管理架构

不用 Redux / MobX / vuex，用**最小可测的单例＋订阅**：

```js
// store.js —— 50 行够了，别上框架
let state = load() || { plan:{}, events:[], expenses:[], transfers:[], specials:[], closed:{} };
const subs = new Set();
export const subscribe = fn => (subs.add(fn), () => subs.delete(fn));
export const commit  = (mut, tag) => { mut(state); persist(state); subs.forEach(f => f(state, tag)); };
export const read    = sel => sel(state);
```

页面侧：

```js
Page({
  onLoad()  { this.unsub = subscribe(s => this.paint(s)); },
  onUnload(){ this.unsub(); },
  paint(s)  {
    const v = deriveToday(s);                       // 领域层算
    this.setData({ left: v.left, pct: v.pct });     // 只 set 变化字段
  }
});
```

数据流严格单向：

```
UI 事件 → action → commit(改 state ＋ 落 storage) → notify → setData → UI
             ↑ 只有 action 能写；只有 domain 能算；UI 不算账
```

## 六、数据架构：追加式账本 ＋ 派生余额

```
写入（只追加，不改历史）
  Expense[]   支出   {date, category, amount(分), daySlot}
  Transfer[]  划转   {date, from, to, amount, kind}
  Special[]   专项   {date, amount, reason, account:POCKET}
        │
        ▼  ledger.js 聚合（纯函数）
派生（每次现算＋记忆化，不落库）
  DaySlot      当日额度 / 已花 / 结余 / closed
  PoolBalance  ②＝Σbudget − Σspent
  PocketBal    ③＝Σpayday_save ＋ Σpool_clear − Σspecial
  PayEventView 本期应存＝totalIn − billTotal − 55.19×days − specialOut
```

**为什么用追加式而不是「直接改余额」**：
- 记错一笔 → 追加一条更正，历史不被覆盖，**可审计**
- 校准真实余额 → 写一条 `Adjust{diff}`，而不是偷偷改 PocketBal
- 想改日额度（55.19→60）→ 只改 Plan，派生层自动重算全表
- 导 CSV / 换机恢复 → 导出的是流水不是快照，永不矛盾

账户建模（关键：三类账户是**枚举**，不是三张表）：

```js
const ACCT = { BANK1:'工资卡', POOL2:'余额宝', POCKET3:'小荷包',
               BILL:'账单平台', OUT:'外部支出' };
// 「还花呗」= Transfer(BANK1 → BILL) —— 不是 Expense，务必写进枚举注释
```

## 七、领域层算法（技术含量全在这里）

### 7.1 金额：分存整数，全项目唯一取整处

```js
// utils/money.js —— 全项目唯一允许出现 Math.round 的地方
export const yuanToFen = y => Math.round(y * 100);
export const fenToYuan = f => (f / 100).toFixed(2);
export const sumFen    = a => a.reduce((s, x) => s + x.amount, 0);   // 全程整数
```

日额度写成常量 `RATE_FEN = 5519`；`budgetOf(days) = 5519 * days` 恒为整数，**不存在任何浮点累加路径**。

### 7.2 日历引擎：提前发薪是算法，不是配置

```js
export const HOLIDAY = {
  '2026-09-25':{type:'假',name:'中秋'}, '2026-09-26':{type:'假'}, '2026-09-27':{type:'假'},
  '2026-10-01':{type:'假',name:'国庆'}, /* 10/2 … 10/7 */
  '2026-09-20':{type:'补班'},   // ← 国庆调休，计为工作日
  '2026-10-10':{type:'补班'},
  '2027-01-01':{type:'假',name:'元旦'}
};
// 25 号逢休息日/法定假 → 前推到最近工作日
export function actualPayDay(y, m) {
  let d = new Date(Date.UTC(y, m - 1, 25));
  while (isRest(d) || isHoliday(d)) d.setUTCDate(d.getUTCDate() - 1);
  return iso(d);
}
// 计薪工作日 = 周一~五 − 法定假 ＋ 调休补班   ← 台账那套规则代码化
export function workDays(start, end) { /* … */ }
```

**这是全 App 最容易错、也最该测的模块。**

### 7.3 区间天数（回答「为什么每期预算不一样」）

```js
range  = [本期 actualPayDay, 下期 actualPayDay − 1]   // 含首尾
days   = diffInDays(range)                            // 29 / 33 / 30 / 31 / 12
budget = RATE_FEN * days
```

最后一期是特例：`range_end = deadline(2027-02-05)`，不是下个发薪日 → 所以只有 12 天。**必须在 plan.js 里写死并注释清楚。**

## 八、持久层与版本迁移

```js
const KEY = 'p5519', SCHEMA = 3;      // 数据结构每变一次 +1
export function load() {
  const raw = wx.getStorageSync(KEY);
  if (!raw) return seed();            // 首次：注入 data/plan-2026.json
  return migrate(JSON.parse(raw));    // v1 → v2 → v3 逐版升级
}
export function persist(s) {          // 写失败则降级为纯内存，不崩
  try { wx.setStorageSync(KEY, JSON.stringify(s)); } catch (e) { markDirty(); }
}
```

| 要点 | 说明 |
|---|---|
| **必须带 schemaVersion** | 半年后加功能，老数据不迁移会直接白屏 |
| storage 上限 10MB | 一天 5 笔 × 一年 ≈ 200KB，**绰绰有余** |
| 立即写、不节流 | 记一笔是低频操作，丢一条比卡一下严重 |
| 冷启动优化 | app.onLaunch 里 load＋seed 完成即就绪，页面只读派生 |

## 九、提醒架构（这里有个真实的坑）

微信**长期订阅消息**只对部分类目（政务/医疗/交通/金融/教育等）开放，**个人主体的工具类小程序通常只能用「一次性订阅」**：用户授权一次，你只能发一条。

所以提醒这样设计：

```
主方案：一次性订阅 ＋ 顺手续订
  · 每次「记一笔」累计计数
  · 攒到第 3 笔时弹「是否接收下次结算提醒」
  · 引导勾选「总是保持以上选择，不再询问」→ 之后可静默续订

兜底方案（永远可用，不依赖推送）★推荐当一等功能
  · 小程序图标右上角角点（今日未结算就 +1）
  · 导出一张 .ics：把 5 个发薪日写进手机系统日历，
    标题直接写「转③ 1,855」
```

> 说实话：**系统日历比订阅消息可靠得多。** 别把宝押在推送上。

## 十、云开发（阶段二再加，可选）

```
云开发环境（TCB）
 ├─ 云数据库  集合 user_state，docId = openid   ← 整包快照，用于跨设备恢复
 ├─ 云函数    backup.js / restore.js            ← 只这两个，业务逻辑不放云上
 └─ 云存储    export/xxx.csv                    ← 可选
```

| 原则 | 原因 |
|---|---|
| **云只存快照，计算全在本地** | 避免网络延迟阻塞记账；离线永远可用 |
| 权限设「仅创建者可读写」 | 你的钱的数据不能给别人看 |
| 不同步「实时余额」 | 小程序本来也读不到银行余额 |
| 走 `wx.cloud` 而不是 `wx.request` | 后者要配 HTTPS 域名白名单＋ICP 备案，纯找麻烦 |

```js

```

必测清单：

## 十三、性能预算

| 指标 | 目标 | 实现 |
|---|---|---|
| 冷启动到「今日」可点 | < 1.5s | onLaunch 同步读 storage；首屏零网络请求 |
| 记一笔 → 数字更新 | < 120ms | 局部 setData（只传 left / pct） |
| 主包体积 | < 300KB | 无 UI 框架、无 ECharts、图标纯 CSS |
| 存储占用 | < 1MB | 只存流水与快照 |

## 十四、明确不用的东西（防过度设计）

❌ Redux / MobX / vuex —— 单例＋订阅 50 行足够
❌ UI 组件库（Vant / WeUI）—— 只需 5 个自定义组件，引库反而包大、风格失控
❌ ECharts —— 一个环＋一组柱子，Canvas 手写 60 行
❌ 自建服务器 / Nginx / MySQL —— 单人用，纯属负担
❌ 手机号登录、云函数鉴权 —— openid 天然隔离
❌ 多人协作 / 账本共享 / 社交 —— 你不需要
❌ 图表分析 / AI 记账 / 语音记账 / OCR 账单 —— 会让它变成另一个随手记
